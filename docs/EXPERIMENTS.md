## SEGA エモジャムの ESP32-S3 化(断念)

- 対象: SEGA の玩具「エモジャム」
- 試したこと: 技適番号から ESP32-S3-WROOM-1 搭載と当たりを付け、
  分解してモジュールを確認。ピンを辿って純正ファームの吸い出し
  までは成功
- 結果: フラッシュへの書き込みができず断念
- 分かったこと: 読めるのに書けない状態だった
- 知りたいこと: 書込不可の原因が何か。espefuse.py の summary で
  Secure Boot / Flash Encryption の eFuse 状態を見れば切り分け
  できるはず。フラッシュチップ側の保護ビットだけなら解除の
  可能性があり、Secure Boot 有効だと署名鍵なしでは原則詰み、
  と予想している(未確認)
- 次に試すなら: モジュール自体の載せ替え。新しい WROOM-1 なら
  eFuse 未焼成でロックが無いので一番確実(後回し中)

## 2026-10-29 MeshCore 実験 Stage 1(受信のみ)

- 対象: T-Deck v12(MeshCore リスニングプロファイル)
- 試したこと: 920.8 MHz / BW62.5 / SF8 / CR 4/5 で受信専用にし、
  生パケットを RAW ログ画面に記録。相手は WADAMESH を焼いた
  もう1台の T-Deck を想定
- 結果: 成功(2026-10-29 夜、実機確認)。WADAMESH の ADVERT を
  受信できた: 111 バイト、RSSI -40dBm、先頭バイト 0x12
  (MeshCore ヘッダとして読むとタイプ 4 = ADVERT、経路長 0)。
  周波数 / BW / SF の物理層互換を確認
- 分かったこと: WADAMESH 側の CR 表示は 4 のままだった
  (5 に変更したつもりが未適用。フィールドは「離れたときに適用」
  される仕様)。それでも受信できたのは、LoRa の明示ヘッダに
  ペイロード側の CR が含まれ、受信機が自動で追従するためと
  みられる。受信の成否を決めるのは周波数 / BW / SF / 同期
  ワードで、CR の受信側設定への依存は小さい。ただし
  「両側 CR 4/5」という条件自体は未検証なので、CR=5 を
  確定させてからの再送確認が次の一手。Stage 2(ADVERT 解読)は
  今回捕捉したパケットから始められる
- 追記(同日夜): WADAMESH の CR を 5 に確定させて再送した
  ADVERT も受信(111B、-47dBm)。両側 CR 4/5 の条件でも受信を
  確認した。あわせて 12 バイトの別パケット(ヘッダのタイプ 11、
  -33dBm)も捕捉しており、MeshCore の実トラフィックを複数種
  聞けている
- Stage 2 着手(2026-10-29): T-Deck v13 を配信(コンパイル検証済み、
  flash 39%)。RAW バッファを 160 バイトに拡張し、ADVERT を
  その場でパースして公開鍵先頭・送信時刻(UTC)・ノード名を
  RAW 画面に表示する。署名(Ed25519)の検証はまだしない。
  実機で WADAMESH のノード名が読めるか確認待ち

## 2026-10-31 T-Deck v15/v16 実機確認（無印 + Plus）

- 対象: ENZ_TDECK_v16（v15 の上位互換として一括確認）、無印1台 + Plus 1台
- 試したこと: v16 を2台に Launcher SD インストールし、7項目を確認
- 結果:
  - RF スキャナ（v15）: 両台でバー表示と PEAK 表示が動作。自宅では
    自前ノード群のため帯域全体が強く出る（920.6 MHz で -1 dBm 観測）
  - SOS（v15）: 無印から NOFIX 形式で送信、Plus のホーム画面に
    赤字で受信。ESP-NOW 経路を確認
  - ピア RSSI 近接表示（v15）: 両方向で -39 / -42 dBm、NEAR 表示 OK
  - ES7210 マイク初期化（v16）: 音声が通ったことで初期化成功を確認
  - 音声 PTT（v16）: 双方向に音声が通った。ただし音量が小さい
    （マイクゲイン暫定 24 dB のため。次版でゲイン改修）
  - マイク使用後のトラックボール中央押し: 両台とも正常。
    メーカー注意書きの GPIO0 競合は発生しなかった
  - MeshCore RAW の SD ログ（v15）: 当夜は Plus の LoRa 受信が 0 パケットで、
    SD を読み出してもログファイル自体が生成されていなかった。
    仕組みの不具合ではなく、記録すべき受信が無かったため。後日再確認
- 分かったこと: SD の無い個体では jpfont16.bin が読めず日本語が
  豆腐になる（仕様どおり）。日本語フォントと SKK 辞書は SD 必須

## 2026-10-31 T-Deck v17 実機確認（音声ゲイン）

- 対象: ENZ_TDECK_v17（無印 + Plus、Launcher SD インストール）
- 試したこと: マイク PGA 24→36 dB 化と再生ゲイン（Voice Vol、初期 ×2）の効果確認
- 結果:
  - 音声 PTT は双方向に聞こえる（実用確認）。雑音は多め
  - 音量は v16 と体感で違いなし — ゲイン変更の効果は確認できず
- 分かったこと（未確定の考察）: ボトルネックは再生側ゲインより
  取り込み側の音量レベル、またはスピーカー/アンプの物理限界の可能性。
  次の候補: 送信側 PCM デジタルゲイン、ノイズゲート/ハイパス、
  Voice Vol ×4 での切り分け
  - 追加切り分け（同日）: Voice Vol ×4 では少し大きくなったが雑音が
    かなり酷くなった。再生側（スピーカー/アンプ）には余力があり、
    本丸は取り込み側の S/N と確定。v18 は送信側処理
    （ADPCM 前のハイパス + ノイズゲート + デジタルゲイン）で攻める

## 2026-10-31 T-Deck v18 実機確認（音声・非対称の発見）

- 対象: ENZ_TDECK_v18、無印 + Plus、どちらも Voice Vol ×4
- 結果（方向で非対称）:
  - Plus → 無印: 音量は大きく出る（無印は筐体の都合で薄型スピーカーに
    換装済み）。雑音も大きいが声はギリギリ聞こえる
  - 無印 → Plus: 音量小さめで雑音が勝ち、実用できないレベル
  - ユーザー評: 「遠距離で市民ラジオしてるみたい」
- 分かったこと: 問題はファーム共通ではなく主に「無印の送信（マイク
  取り込み）」側。無印は開腹・スピーカー換装歴のある個体
- 次の容疑者: ADC1+ADC2 の平均処理。片スロットがノイズ源（または
  マイク無しチャンネル）なら両台とも損をし、無印の個体差で悪化する。
  v19 で Mic Ch（AVG/CH1/CH2）切替を入れて切り分ける
